### Isolated application-database growth measurements

[Lms.RosterBenchmark](../../tools/Lms.RosterBenchmark/README.md) now loads the full registered records into a new SQLite database using the current application schema/indexes and measures the actual admin directory service queries. Source payloads and exact business types remain in a benchmark evidence table where the current application model lacks equivalent fields. It does not alter the live application database.

The first verified four-state run loaded **27,365 individual credentials, 4,689 business licenses and one explicitly evidenced affiliation**, totaling 32,054 credential identities. Including schema/indexes and full source evidence, the database occupied **58,048,512 bytes (58.05 MB decimal)**. |---|---:|---:|---:|

At the user's request, use the largest comparable saved real-estate roster rather than averaging small samples. Officer roles can share a Broker license number. Type/number counts are credential-role keys, not unique people; even type/number duplicates may retain different appointments/status/dates and must not be flattened by the estimate. Current-list relationship keys are published references, not all verified/resolved graph edges; separate broker-associate relationships are not included in this count. Source scope is the four current-list types, not MLO endorsements, examinees or education categories.

This gives a **22.1-million-key capacity scenario**, with **3.73 GB decimal (about 3.47 GiB) of raw CSV-equivalent source storage**, for 50 states plus D.C. and Puerto Rico. It is intentionally California-sized, not a representative average or statistical upper bound. It is **not a measured database-size estimate**: actual application tables, preserved relationship/appointment rows, indexes, snapshots/history and operational data require an isolated full import and measurement. No database was modified or query latency measured for this calculation. California's source use restrictions remain applicable.
